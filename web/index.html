RFTP - Reliable File Transfer Protocol

RFTP is the application-layer protocol designed in this project. It runs inside UDP datagrams and adds what UDP lacks: sequence numbers, acknowledgements, timeout-and-retransmission, duplicate handling and error detection (CRC-32 per packet, SHA-256 for the whole file). Everything on this page is generated from the real protocol code (rftp_common.py, rftp_client.py, rftp_server.py).

10 ...Datafile chunk (up to 1024 B), JSON for META, empty for ACK

How a packet is checked

  1. Receiver splits the 10-byte header from the data.
  2. It recomputes CRC-32 over type + flags + seq + data.
  3. Match: packet is accepted and acknowledged.
  4. Mismatch: packet is discarded with no ACK, so the sender's timer expires and it retransmits.

The algorithm (as implemented)

Sender
send META (seq 0): name, size, packets, SHA-256
for n = 1 .. N:
    packet = [DATA | EOF if last | n | CRC-32 | chunk n]
    attempts = 0
    loop:
        send(packet);  start timer (default 0.3 s)
        wait for ACK:
            valid ACK with seq == n  -> next chunk
            corrupted or stale ACK   -> ignore, keep waiting
        timer expired:
            retransmissions += 1;  attempts += 1
            if attempts > 15: abort (FAILED)
Receiver
on every UDP datagram:
    if CRC-32 does not match -> discard, send no ACK
    if type == META:
        new transfer id -> create session
        send ACK 0   (also for a repeated META)
    if type == DATA, seq n:
        if n already stored -> duplicate: ignore the data
        else                -> store chunk n
        send ACK n   (always: the earlier ACK may be lost)
        if all N chunks stored:
            write file in order, verify SHA-256

NS2 vs Python sockets vs theory

Stop-and-wait with loss p on both the data and ACK path: success probability per attempt = (1-p)², so expected retransmissions = (N+1)·(1/(1-p)² − 1). Both implementations follow the theory.

Architecture

💻 Client (sender)

  1. Select file
  2. Split into chunks
  3. Build packet: seq + data + CRC-32
  4. Send via UDP, start timer
  5. ACK in time? next packet — else retransmit
⇄

🌐 UDP network

Best effort only. Packets can be lost, corrupted or delayed. We simulate this with sockets (LossySocket) and with NS2 (ErrorModel).
⇄

🗄️ Server (receiver)

  1. Receive UDP packet
  2. Validate CRC-32 (bad → discard, no ACK)
  3. Check seq: new → store, duplicate → ignore
  4. Send ACK(seq) — also for duplicates
  5. All packets in → rebuild file, verify SHA-256

Stop-and-wait ARQ – one round

  1. Client sends DATA(n) and starts the timer.
  2. Server checks CRC; if OK and new, stores the data. A duplicate is ignored but still acknowledged (the earlier ACK may have been lost).
  3. Server replies ACK(n).
  4. ACK arrives → client sends DATA(n+1). Timer fires first → client resends DATA(n) (max 15 retries).
  5. After the last packet, the server writes the file and the SHA-256 is compared with the original.
